## Rules that are easy to break

- **Terraform vs Wrangler:** Terraform manages AWS and Cloudflare zone/DNS/rules; the Worker script and route are deployed with Wrangler only. Never manage the same resource with both.
- **Security headers live in the Worker only**, not in the Cloudflare dashboard or Astro. CI asserts all six.
- **No `'unsafe-inline'`:** Astro uses `build.inlineStylesheets: 'never'`; CSP stays `style-src 'self'`. Don't add third-party origins without a reason.
- **No long-lived AWS keys in CI:** GitHub Actions uses OIDC. The Worker IAM user's key is the one exception; it lives only in Worker secrets, never in Terraform outputs or the repo.
- **GDPR:** EU region, self-hosted fonts (Fontsource), cookieless analytics. No Google Fonts or other trackers. Turnstile is the one third-party script: it loads only when someone starts on the contact form (e2e checks this). The contact Lambda never logs names, addresses or messages.
- **Credentials:** show claims plus the issuer's verification link, never the certificate files (the diploma prints a date of birth; the PDFs in `cv/reference/` are git-ignored). The AWS Certified Solutions Architect – Associate card is "In progress" with no emblem; the official badge may only be shown once the exam is passed (then add it to `site/src/credentials.ts`).
- **Legal pages:** the privacy policy `/datenschutz/` (EN, DE, `LegalPage.astro`) is `noindex` and out of the sitemap, and must match what the site does: when a third party, cookie, stored key or data flow changes, update both languages in the same PR. The Impressum is not built: it needs a serviceable address, and the owner's home address stays private. Never put that address on the site, in the repo or in a PR.
- **CV is public:** `cv/data.yaml` and the PDFs are published. Never add a phone number, street address, date of birth or private email address; `cv/check.sh` fails the build on those. `cv/reference/` is git-ignored and holds the owner's originals: never commit it. Its PDFs were public until the history rewrite of 2026-11-08. Check `git ls-files` before calling any file private. Keep Sorted's availability claims in line with its case study (Multi-AZ is designed, not running).
- **Case studies:** private repositories use `repoPrivate: true` (the page says "private repository"), never a link. Screenshots go through `ThemedScreenshot` (one image in the text; `dark` optional; `placement="natural"` shows it 1:1 at its own pixel width, shrinking only on screens narrower than the image) or `ScreenshotGallery` (a sideways-scrolling row of cards, one full card plus a quarter of the next, optional badge such as "Demo data" on every screenshot; each screenshot is a link to its full-size WebP, opened in a native `<dialog>` lightbox, fitted to the window with an "Actual size" toggle when the image is larger, and without JavaScript the link opens the image itself); both take light/dark pairs and emit WebP under `/_astro/`. Cost figures stay labelled as estimates.
- **Case studies are DevOps first:** the portfolio sells Cloud & DevOps engineering, not software development. Lead with the platform (infrastructure, pipelines, security, cost, operations); the application is "the workload" and comes after the infrastructure. Outcomes are infrastructure figures (environments from one module, long-lived keys, Terraform tests, cost estimates), not commit or app test counts. Sorted is a commercial product (live, commercially available at `sorted.onl`): say so, and never write the old "training project" wording. Claims about customers, revenue or traffic only when the owner states them as fact; screenshots of dashboards never imply users. Showroom+ is not mentioned in case studies (it is not DevOps work); the CV lists it in its work history. Keep the honest Limitations section.
- **Diagrams (React Flow):** never use `@astrojs/react` or `client:*` islands; they emit an inline script, an inline `<style>` and a `style` attribute that the CSP (`script-src 'self'`, `style-src 'self'`) rejects. Diagrams are typed data in `site/src/diagrams/`, mounted by the plain module script `mount.ts` when they scroll into view, via `ArchitectureDiagram.astro`. Colours come from the site tokens. Use official icons and logos unmodified, each folder with a README: AWS Architecture Icons (`site/src/assets/aws-icons/`, release 07312026, also the generic Users and Email icons), the GitHub Invertocat (`github-logo/`, black/white by theme) and the Cloudflare logo (`cloudflare-logo/`, on a white plate because the wordmark is black). No invented or recoloured symbols. A diagram wider than a phone can set `focusNode`; the sideways-scrolling figure then opens centred on that node. Every diagram caption starts with "Simplified diagram." (`diagramSimplified` in i18n). Every diagram needs a text alternative in EN and DE. Mouse drag pans only after zooming in past the fitted view (fine pointer only), Ctrl/Cmd+wheel zooms, a touch swipe must keep scrolling the page. `tests/e2e/diagram.spec.ts` enforces the production CSP, so any violation fails the build. Diagram-page JS is about 128 KB gzipped (proposed budget 140 KB); pages without a diagram load none. A diagram can define `paths` (buttons above it trace one path and dim the rest via `vdd-on`/`vdd-dim` classes; the buttons stay `hidden` until the diagram mounts). Four diagrams exist: `site-platform` (this site, `compact`, paths Requests, Contact and alerts, Deploys; the Worker and Lambda are text-only nodes), `rainalert-release` (`compact`, paths Releases and Requests; Docker Hub, Render and the weather APIs are text-only nodes, no official icon in the repo), `sorted-production` (paths: Requests, Mail, Releases; Region > VPC > public and private subnets; group boxes take a `variant`: only `cloud` shows the AWS Cloud icon, `vpc`/`public`/`private` are labelled boxes) and `sorted-release` (`compact` canvas, horizontal zoom buttons, more fitView padding). On phones the canvas is at least 68rem wide so diagram text stays ≥10px (e2e floor); widen it rather than lowering the floor when a diagram grows.
- **Bilingual:** `/` is EN, `/de/` is DE. User-facing strings go in `site/src/i18n/{en,de}.ts`; hero, contact and work-with-me must exist in both.
- **Theme:** dark is the default whatever the device setting (owner's decision, 2026-11-06): `:root` has `color-scheme: dark`, and only the header switch turns light on (`data-theme="light"` on `<html>`, saved in `localStorage`, re-applied before paint by `public/theme.js`). Tokens use `light-dark()`. In e2e, pick a theme with `themeState()` / `useTheme()` from `tests/e2e/theme-state.ts`, not by emulating `colorScheme` (the site ignores it). Never theme with `prefers-color-scheme` media queries or `dark:` (they ignore the switch); theme-specific media uses `.only-light` / `.only-dark`.
- **Tailwind v4:** CSS-first config in `site/src/styles/global.css` (`@theme`), no `tailwind.config.js`. Use semantic tokens (`bg-bg text-fg`) instead of `dark:` on every element; extract components, not `@apply` classes.
- **Case studies:** the owner's source notes live in `case-studies/`: the write-ups as `<Name>-Case-Study.md` at the top level, raw images in `cs_<project>/screenshots/` (RainAlert: 3 flat images with no theme pairs, an AI-generated London puddle illustration, the app on its street background and a small panel crop). Sorted's 7 light/dark pairs are already in `site/src/assets/case-studies/sorted/`; RainAlert's copies are in `site/src/assets/case-studies/rainalert/`. `ScreenshotGallery` takes `dark` as optional, so single images show in both themes. They are the only source of facts: write MDX from them, never invent. The site content is MDX in `site/src/content/case-studies/{en,de}/<slug>.mdx` (schema in `site/src/content.config.ts`, language = folder). `draft: true` entries are left out of production builds; `SHOW_DRAFTS=1` (and `dev`) includes them. The e2e build is the production build, without drafts, and tests Sorted in both languages. Screenshots must go through Astro's image pipeline (resized, WebP/AVIF, `width`/`height` set, lazy-loaded) into `/_astro/`; never copy the raw PNGs into `public/` (page-weight budget in Phase 9). Where light/dark pairs exist (Sorted), render both with `.only-light` / `.only-dark` (they follow the header switch; never `<picture>` with a `prefers-color-scheme` source, which ignores the switch); single images (RainAlert) are shown as they are. Give every image real alt text, and resize the multi-megabyte ones hard (they are far larger than any layout width). Keep `case-studies/` out of the deployed site and out of Prettier
- **Work with me grid:** each service in `hireServices` (i18n) has `proof`, a section anchor per project, in each language; a lit dot links there. A dot is a claim: add one only when that section really shows the service (e2e checks that the target exists, not that it is true). A service shown only outside the three case studies (Kubernetes: `source`, linking `sre-project`) has no dots and comes last. The offer's facts are the owner's (2026-11-08); it names no clients beyond the three projects.
- **Links to other sites open in a new tab and say so to screen readers:** use `ExternalLink.astro`, `CTAButton` with `external`, or `target="_blank"` with `rel="noopener noreferrer"` and an sr-only `opensNewTab` (the owner's preference; e2e checks GitHub, LinkedIn, the policy and source links). In prose pages Prettier can put a space before punctuation after a component link, so plain `<a>` is safer there.
- **Mobile first:** unprefixed utilities target ~360px; touch targets ≥44px; nothing hover-only.
- **Hero headline:** the `h1` is the name alone (the e2e test checks it); the role is a paragraph styled to the same width. Widths are fixed ratios: the name is sized in container units of the text column (`12.3cqi`, capped at `4.5rem`), the role at `0.674em` (EN) and `0.63em` (DE) of it (DM Sans 500). Re-measure the ratios if the name, the role wording or the heading font changes.
- **Hero diagram:** `HeroArchitecture.astro` with data in `site/src/diagrams/hero-variants.ts`, made up and decorative (`aria-hidden`). Official AWS icons only (same release as the case-study diagram); groups without an official icon are labelled boxes. No style attributes: bar and node geometry are SVG attributes, the random pick toggles a class.

## Workflow

- Small PRs, one task each; `main` is always deployable and protected.
- Branch every PR from `main` and target `main`; never stack PRs on other PR branches (the owner merges in batches, so stacked PRs land in dead branches; #32 and #35 had to be recovered in #36).
- Quality gates (Lighthouse mobile, axe, Playwright, html-validate, Trivy/Checkov, gitleaks) fail the build; don't weaken a threshold to get green.

## Commands

`pnpm install`, `pnpm lint`, `pnpm format:check` (root). CV: `cv/build.sh`, `cv/check.sh` (need `typst`, and `poppler-utils` for the check); the site's `build` runs `cv/build.sh`, so it needs Typst too. Lighthouse: build the site, then `CHROME_PATH=<chrome> pnpm --filter @vdd/e2e lighthouse`. Deploys run from `.github/workflows/deploy.yml` on every push to `main`.
