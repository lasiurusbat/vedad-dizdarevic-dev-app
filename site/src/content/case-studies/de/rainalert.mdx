## Architektur

Zwei Pfade laufen durch Rain Alert: Releases und Anfragen. Die Schaltflächen über dem Diagramm zeichnen jeden davon nach und blenden den Rest ab. Es gibt keine Datenbank und keine serverseitige Session; die App ist zustandslos.

## Einmal bauen, genau dieses Image ausliefern

<TradeOff
  gained="Das Image, das die Tests bestanden hat, ist das Image, das läuft. Zwischen CI und Produktion wird nichts neu gebaut."
  price="Chrome läuft im schlanken Image nicht, deshalb laufen die Browser-Tests auf dem Runner, bevor irgendetwas hochgeladen wird."
/>

Jede Prüfung läuft gegen das Image, das ausgeliefert wird.

- **Zwei Stufen.** Die erste Stufe baut Wheels; die Laufzeitstufe installiert daraus mit `--no-index`, sodass das Image keinen Compiler und keine Systempakete enthält.
- **Ohne Root.** Die App läuft als Systembenutzer ohne Login-Shell und braucht keinen beschreibbaren Pfad.
- **Selbstbeschreibend.** Version und Commit sind Build-Argumente und stehen in den OCI-Labels, in der Umgebung und im Footer jeder Seite. Image, Registry und laufende Website nennen denselben Build, und der Smoke-Test liest die Version aus diesem Footer.
- **Ein Health-Check, der Upstreams ignoriert.** Er ruft die Startseite ab, die keinen externen Dienst anfragt, sodass ein Ausfall einer Wetter-API einen gesunden Container nie als ungesund markiert.
- **Dasselbe Image lokal.** Docker Compose baut die App und einen Testdienst aus einem gemeinsamen Anker, mit `pull_policy: build`, sodass ein Testlauf nie ein veraltetes lokales Image nutzt.

## Ein Release ist ein Git-Tag

<TradeOff
  gained="Ein Release ist ein einziger Befehl, und nur geprüfter Code auf main kann zum Release werden."
  price="Ein erneut gestartetes Release baut den getaggten Commit, nicht den danach nachgeschobenen Fix. Ein veröffentlichter Tag wird nie verschoben, deshalb kostet ein Fehler eine neue Versionsnummer."
/>

Ein GitHub-Actions-Workflow verhält sich auf zwei Arten. Ein Pull Request oder ein Push auf `main` baut das Image, führt die Offline-Tests darin und die Browser-Tests auf dem Runner aus und hört dann auf. Ein Tag geht weiter:

1. Derselbe Build und dieselben Tests.
2. Der Tag muss gültig sein und auf `main` liegen.
3. Das getestete Image wird unter diesem Tag nach Docker Hub hochgeladen.
4. Der Deploy-Job übernimmt.

Vier Regeln sichern das ab:

- **Ein Gate, das nicht leer bestehen kann.** Eine übersprungene Testsuite würde trotzdem Erfolg melden, deshalb lässt ein fehlender Browser den Lauf scheitern.
- **Ein Image-Tag pro Release.** Semantische Tags, nie `latest`, nie ein erneut hochgeladener Tag.
- **Releases werden nie mittendrin abgebrochen.** Neuere Pushes brechen veraltete Läufe ab, außer bei Tags.
- **Updates laufen durch dasselbe Gate.** Dependabot öffnet wöchentlich gebündelte Pull Requests für Actions, pip und das Basis-Image, und jeder wird nur gemergt, wenn die Pipeline grün ist.

## Das Ergebnis prüfen, nicht die Aktion

<TradeOff
  gained="Ein Deployment zählt erst, wenn die Live-Domain mit der neuen Version antwortet, nicht wenn ein Hook 200 zurückgibt."
  price="Eine langsame DNS-Änderung oder ein langsamer Image-Wechsel lässt den Release-Lauf scheitern, obwohl das Deployment selbst geklappt hat. Das Runbook erklärt, wie dieser Fehler zu lesen ist."
/>

Der Render-Dienst basiert auf einem Image: Render holt es von Docker Hub und führt das Dockerfile nie aus. Zwei Render-Einstellungen machen das möglich:

- **Auto-Deploy ist aus.** Wäre es an, würde jedes hochgeladene Image den gespeicherten Rückfall-Tag neu ausrollen, und genau so kommt eine alte Version still zurück.
- **Ein Deployment ist ein Hook-Aufruf mit dem exakten Image-Tag.** Eine neue Image-URL in den Render-Einstellungen zu speichern, rollt nichts aus, und der alte Container läuft ohne jedes Anzeichen weiter.

Nach dem Hook fragt der Smoke-Test die Live-Domain bis zu drei Minuten lang ab (12 Versuche im Abstand von 15 Sekunden), bis die Seite `Version X.Y.Z` anzeigt.

## Im Zweifel geschlossen

<TradeOff
  gained="Pull Requests, auch aus Forks und von Dependabot, können nie ein Image hochladen oder ausrollen."
  price="Jedes Secret wird von Hand gesetzt, in GitHub und im Render-Dashboard. Fehlende und zu eng berechtigte Secrets haben das erste Release zweimal scheitern lassen."
/>

- **Secrets nur bei Tag-Läufen.** Das Workflow-Token darf nur lesen, und der Deploy-Job läuft in einer Umgebung `production`, in der verpflichtende Reviewer eine Einstellung entfernt sind.
- **Sicherheits-Header auf jeder Antwort.** Eine Content Security Policy mit `default-src 'none'`, alles andere `'self'` und kein `unsafe-inline`, dazu `X-Frame-Options`, `nosniff`, eine Referrer- und eine Permissions-Policy. Ein Test schlägt fehl, wenn sich ein Header ändert.
- **HSTS mit Bedacht.** Es wird nur über HTTPS gesendet und ohne `includeSubDomains`, sodass ein Fehler die anderen Nutzungen der Domain nicht sperren kann.
- **Keine Anfragen an Dritte.** Die Schriften werden selbst gehostet.
- **Der API-Schlüssel landet nie in einem Log.** Er steht in einem Query-String, deshalb protokolliert der Code nur Statuscodes und Exception-Klassen. Ein Test schlägt fehl, wenn ein Schlüssel im Log landet.

## Kostenlose Tarife, die gut ausfallen

<TradeOff
  gained="Hosting und CI kosten nichts, bei jedem Dienst."
  price="Ratenlimits, die ich nicht anheben kann. Am 29. Oktober schlug jede Live-Vorhersage fehl: Die kostenlose Vorhersage-API begrenzt nach IP, und die ausgehende IP von Render ist geteilt."
/>

Die Antwort auf diesen Vorfall kam in Schichten:

1. **Sichtbar machen.** Der Fehlergrund wird jetzt protokolliert, sodass der nächste Fall aus den Logs diagnostiziert wird statt geraten.
2. **Weniger anfragen.** Ein serverseitiger Cache hält eine gute Vorhersage zehn Minuten lang; Fehler werden nie gecacht. Crawler bekommen eine Crawl-Verzögerung.
3. **Eine zweite Quelle.** Wenn Open-Meteo ablehnt, antwortet OpenWeather, übersetzt in das Format von Open-Meteo, sodass oberhalb des Clients nichts erfährt, wer geantwortet hat. Es hat ein eigenes Tagesbudget von 900 Aufrufen, weil dieser Anbieter über den kostenlosen Tarif hinaus abrechnet. Werte, die es nicht liefern kann, bleiben leer.
4. **Ehrlich herunterfahren.** Ein kaputter Upstream liefert `503` und eine fehlende Stadt `404`, nie eine `200`, die „nicht gefunden“ sagt.

Ein Uptime-Check ruft die Startseite ab. Sie fragt keine externe API an, deshalb belegt er DNS, Zertifikat und Version, und er hält die kostenlose Instanz wach.

## Probleme, auf die ich gestoßen bin

Das erste Release brauchte fünf Anläufe, und jeder Fehler war ein fehlendes Stück der Pipeline, kein Fehler in der Anwendung. Jedes Release seitdem war beim ersten Anlauf grün.

## Der Workload

<ThemedScreenshot
  light={appPanel}
  placement="natural"
  alt="Das Vorhersage-Panel von Rain Alert für Dublin: der Stadtname, ein Regenhinweis, das Stundendiagramm mit einer Markierung bei 18:00, die Zusammenfassung für heute und die sieben Tage mit ihren Regenwahrscheinlichkeiten."
  caption="Das Vorhersage-Panel, auf dem Server für jeden Tag gerendert, sodass es auch ohne JavaScript funktioniert."

Die Plattform betreibt eine kleine Flask-App. Man gibt eine Stadt ein und sieht die Regenwahrscheinlichkeit für die nächsten sieben Tage und stündlich für heute. Sie kann im Browser benachrichtigen und die Regentage in den Kalender exportieren, und sie lässt sich als Web-App installieren, deren Service Worker die Oberfläche cacht, nie die Vorhersage.

Einstellungen bleiben im Browser, es gibt also keine Konten und keine personenbezogenen Daten auf dem Server. Die Wetterdaten kommen von Open-Meteo unter einer nicht kommerziellen Lizenz, deshalb bleibt die App kostenlos, mit Spenden als einziger Einnahme.
