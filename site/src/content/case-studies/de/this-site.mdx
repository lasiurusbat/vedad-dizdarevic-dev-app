## Ein privater Bucket hinter einem Worker

<TradeOff
  gained="Der Bucket ist nie öffentlich, der Verkehr läuft per HTTPS vom Browser bis S3, und die Edge-Logik ist versionierter, getesteter Code."
  price="Der Worker kann AWS nicht per OIDC erreichen. Er hält deshalb den einzigen langlebigen Zugriffsschlüssel im Setup. Ich rotiere ihn alle 90 Tage von Hand."
/>

Ein öffentlicher S3-Website-Endpunkt spricht unverschlüsseltes HTTP mit seinem Origin, und CloudFront wäre ein zweites CDN hinter Cloudflare. Ein Worker führt die Edge-Logik im kostenlosen Tarif von Cloudflare aus.

- **Signierte Lesezugriffe.** Der Worker signiert jede Anfrage an den S3-REST-Endpunkt mit SigV4 und versucht es einmal erneut. Die Voreinstellung der Bibliothek, zehn Versuche mit Backoff, könnte eine Seite sekundenlang aufhalten.
- **Nur lesen, nichts auflisten.** Sein IAM-User hat zwei Berechtigungen: Objekte lesen und die Kontaktfunktion aufrufen. Ohne `s3:ListBucket` kann niemand auflisten, was im Bucket liegt. S3 beantwortet eine fehlende Seite mit 403, und der Worker liefert dafür die 404-Seite der Website.
- **Saubere URLs.** `/de/projects/sorted/` wird zu seiner `index.html`; `/foo` leitet nur dann auf `/foo/` weiter, wenn die Seite existiert.
- **Zwei Caches.** Gehashte Assets sind ein Jahr lang als unveränderlich gecacht; HTML bleibt fünf Minuten am Edge und wird bei jedem Deploy geleert.
- **Der Bucket selbst.** Block Public Access an, eine Policy, die jede Anfrage ohne TLS ablehnt, Versionierung mit Ablauf alter Versionen nach 30 Tagen und serverseitige Verschlüsselung.

## Security-Header an einer Stelle

<TradeOff
  gained="Eine Quelle für jeden Header, getestet in den Unit-Tests des Workers und nach jedem Deploy noch einmal auf der Live-Domain."
  price="Eine strenge Policy schließt Inline-Skripte und -Styles aus. Theme-Skript, Diagramme und jede dynamische Größe der Website mussten ohne sie gebaut werden."
/>

Header setzt nur der Worker; weder das Cloudflare-Dashboard noch das Framework fügt welche hinzu. Jede Antwort trägt sechs: eine Content Security Policy, HSTS mit Preload, `X-Frame-Options: DENY`, `nosniff`, eine Referrer-Policy und eine Permissions-Policy.

- **Kein `'unsafe-inline'`.** Styles und Skripte kommen vom eigenen Origin. Der Build schreibt keine Inline-Styles, und ein E2E-Test zählt `style`-Attribute.
- **Diagramme unter der Produktions-Policy.** Framework-Islands erzeugen Inline-Skripte, deshalb laden die Diagramme über ein einfaches Modul-Skript, sobald sie ins Bild scrollen. Ein Test lädt sie mit der Produktions-CSP und schlägt bei jedem Verstoß fehl.
- **Erst Report-only.** Die Policy läuft im Report-only-Modus, bis jede Seite in der Browser-Konsole sauber ist; sie durchzusetzen ist eine Änderung in einer Zeile.

## Keine gespeicherten Schlüssel in der CI

<TradeOff
  gained="Jeder Workflow-Lauf bekommt AWS-Zugangsdaten, die mit dem Job ablaufen, und GitHub speichert kein AWS-Geheimnis, das abfließen könnte."
  price="Die Trust-Policies binden numerische GitHub-IDs. Ein Repository umzubenennen oder neu anzulegen heißt deshalb, zuerst die Bootstrap-Variablen anzupassen."
/>

GitHub Actions übernimmt AWS-Rollen per OIDC. Ein kleiner Bootstrap-Stack, einmal von Hand angewendet, legt den Bucket für den Terraform-State und drei Rollen an:

- **`gh-app-deploy`** für den Branch `main` des App-Repositorys. Sie darf Objekte im Website-Bucket auflisten, schreiben und löschen und den Code der Kontaktfunktion aktualisieren, sonst nichts, und den Terraform-State nicht lesen.
- **`gh-infra-plan`** für Pull Requests im Infra-Repository: nur lesend, bis auf die Lock-Datei des States.
- **`gh-infra-apply`** für `main` im Infra-Repository, in einer geschützten Umgebung `production`. Sie darf IAM nur für Namen ändern, die mit `vdd-` beginnen, und kann die CI-Rollen selbst deshalb nicht bearbeiten.

GitHub vergibt inzwischen unveränderliche Subjects (`repo:<owner>@<ownerId>/<repo>@<repoId>`), deshalb vertrauen die Rollen den numerischen IDs von Owner und Repository. Ein neues Repository mit demselben Namen bekommt eine neue ID und keinen Zugriff.

## Zwei Repositories, zwei Pipelines

<TradeOff
  gained="Infrastruktur und Website ändern sich im eigenen Takt, jede mit eigener, eng gefasster Rolle und eigenem Cloudflare-Token."
  price="Die Werte, die die App aus Terraform braucht, etwa Bucket-Name und Rollen-ARN, werden von Hand in die Actions-Variablen der App kopiert."
/>

Terraform verwaltet AWS sowie Zone, DNS und Regeln bei Cloudflare; Wrangler deployt das Worker-Skript und seine Route. Keine Ressource wird von beiden verwaltet.

**App-Repository.** Jeder Pull Request durchläuft Lint und Formatierung, Typprüfung und Build, die Tests des Workers (in der Workers-Laufzeit) und der Kontaktfunktion, Playwright mit axe in beiden Themes und Sprachen sowie gitleaks. Der Build erzeugt außerdem meinen Lebenslauf in beiden Sprachen mit Typst aus einer YAML-Datei, und eine Prüfung schlägt fehl, wenn eine Telefonnummer oder private E-Mail-Adresse in einem PDF auftaucht. Ein Push auf `main` deployt:

1. Die Kontaktfunktion bekommt ihren neuen Code, noch vor dem Worker, der sie aufruft.
2. Danach gehen gehashte Assets hoch, und noch wird nichts gelöscht, damit Seiten aus dem alten Build ihre Dateien weiter finden.
3. Der Rest geht mit `--delete` hoch.
4. Wrangler deployt den Worker, und der Cache wird geleert.
5. Ein Smoke-Test prüft die Live-Domain: alle sechs Header, die 404-Seite, `405` für ein `POST`, die Weiterleitungen von `www` und `http`, dass Bucket und Kontaktfunktion direkten Zugriff ablehnen und dass die Route des Formulars ein erfundenes Turnstile-Token abweist. Er verschickt keine Mail.

**Infra-Repository.** Jeder Pull Request durchläuft `fmt`, `validate`, Trivy, Checkov und gitleaks und postet den Plan als Kommentar. Ein Merge wendet ihn in der geschützten Umgebung an, immer nur ein Lauf gleichzeitig. Das Apply verweigert jeden Plan, der eine Ressource löscht oder ersetzt, bis eine Person ihn mit `allow_destroy` erneut startet. Ausnahmen für die Scanner stehen direkt am Code, jede mit Begründung.

## Sprache ohne Cookie

<TradeOff
  gained="Deutschsprachige Besucher landen ohne Cookie auf der deutschen Startseite, deshalb braucht die Website kein Consent-Banner."
  price="Ohne Gedächtnis landet jemand in Deutschland, der die Startseite später in einem neuen Tab öffnet, wieder auf Deutsch."
/>

Der Worker schickt einen frischen Besuch auf `/` aus Deutschland, Österreich, der Schweiz, Luxemburg oder Liechtenstein mit einem ungecachten `302` nach `/de/`. Deep Links, Klicks innerhalb der Website und URLs mit `?lang=` lässt er in Ruhe. Der Sprachumschalter verlinkt auf `/?lang=en`, deshalb landet ein Klick auf Englisch immer auf Englisch. Crawler, die meist aus den USA kommen, indexieren die englische Startseite.

## Kosten und Alarme auf einem geteilten Konto

<TradeOff
  gained="Der kostenlose Tarif von Cloudflare trägt DNS, TLS, den Edge-Cache und den Worker. Auf AWS nutzt die Website S3, dazu Lambda und SES, wenn jemand eine Nachricht schickt."
  price="Das AWS-Konto teilt sich die Website mit Sorted. Das Budget filtert deshalb auf einen Kostenzuordnungs-Tag, der von Hand aktiviert werden muss. Wird er abgeschaltet, zeigt das Budget ohne Warnung 0 $."
/>

- **Ein Monatsbudget von 5 $** mit Alarm bei 100 % der tatsächlichen und der prognostizierten Kosten, begrenzt auf den `Project`-Tag dieses Projekts.
- **CloudWatch-Alarme** auf Fehler und Drosselungen von Lambda sowie auf Bounce- und Beschwerderate von SES, per SNS an mein Postfach.
- **Ein Uptime-Monitor** prüft die Startseite von außerhalb von AWS und Cloudflare.
- **Mail-Authentifizierung.** SPF, DKIM für den Mailanbieter und für SES sowie DMARC mit Berichten, alles als DNS-Einträge in Terraform.

## Der Workload

Die Plattform liefert eine statische Website aus, gebaut mit Astro: englische und deutsche Seiten, Fallstudien in MDX gegen ein typisiertes Schema und Tailwind CSS. Seiten ohne Diagramm laden kein Framework-JavaScript; die Diagramme laden React Flow erst, wenn sie ins Bild scrollen. Die Schriften sind selbst gehostet, Tracker gibt es keine.
