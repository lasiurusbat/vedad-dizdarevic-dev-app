## Zwei Phasen, eine Codebasis

Das Ziel: für eine Cloud-Zielumgebung bauen, ohne während der Entwicklung für die Cloud zu zahlen. Phase 1 läuft auf einem Raspberry Pi 5 mit Docker Compose, einer kostenlosen Neon-Postgres-Datenbank in Frankfurt und privatem Zugriff über Tailscale. Phase 2 bringt denselben Code auf Lambda, SQS, EventBridge Scheduler, S3 und CloudFront, definiert mit Terraform und ausgeliefert über GitHub OIDC. Pi und Lambda sind beide arm64, daher genügt ein Build-Ziel.

## Vier Ports, alles andere gemeinsam

Nur vier Dinge unterscheiden sich wirklich zwischen Pi und AWS. Jedes ist eine kleine Schnittstelle mit einer Implementierung pro Umgebung. Die Geschäftslogik hängt nur von den Schnittstellen ab, umgebungsspezifischer Code steckt daher ausschließlich in Einstiegspunkten und Adaptern. Postgres ist in beiden Phasen gleich und bekommt deshalb keinen Port.

| Aufgabe | Raspberry Pi | AWS |
| --- | --- | --- |
| Queue | ElasticMQ | SQS |
| Zeitpläne | Cron in einem Container | EventBridge Scheduler |
| Token-Verschlüsselung | lokale AES-GCM-Schlüsseldatei | KMS |
| Ausgehende E-Mail | keine | SES |

Die Queue-Handler sind einfache Funktionen, die einen Batch annehmen und die IDs fehlgeschlagener Nachrichten zurückgeben, also die Form der Lambda-Partial-Batch-Antwort. Auf dem Pi ruft ein Poller sie auf, auf AWS die Lambda-Laufzeit. Der Pi-Adapter ist das AWS SDK, das auf ElasticMQ zeigt; der Pi übt damit bereits den echten Client-Code. Sicherheitsregeln gehören zum Port, nicht zum Adapter: Die Token-Verschlüsselung muss jede Verschlüsselung an Mandant und Verbindung binden, auf dem Pi als Associated Data, auf AWS als KMS-Encryption-Context.

## Isolation durch die Datenbank

In diesem System liegen Namen von Recruitern und E-Mail-Metadaten anderer Menschen. Ein vergessener Filter im Anwendungscode darf daher keine Zeilen eines Mandanten preisgeben. Row-Level Security in Postgres erzwingt die Grenze: eine Policy pro Mandantentabelle, erzwungen und fail-closed, wenn kein Mandant gesetzt ist. Der Mandant wird nur innerhalb einer Transaktion gesetzt und kann so nicht über eine gepoolte Verbindung durchsickern. Fremdschlüssel enthalten die Mandanten-ID, weil Postgres Row-Level Security bei Fremdschlüsselprüfungen nicht anwendet.

Zwei Anwendungsrollen können die Policies nicht umgehen. Sie entstehen in SQL-Migrationen, nie in der Neon-Konsole, weil eine dort angelegte Rolle einer Gruppe beitritt, die Row-Level Security umgeht, und jede Policy unbemerkt wirkungslos würde. Jeder Serverprozess verweigert außerdem den Start, wenn seine Datenbankrolle Superuser ist, Row-Level Security umgeht, Mitglied einer anderen Rolle ist oder Tabellen besitzt. Nur der einmalige Migrations-Job sieht je die Zugangsdaten des Eigentümers.

## Geplante Jobs verteilen sich über die Queue

Hintergrund-Jobs müssen für jeden Mandanten laufen, doch die Mandantenrolle sieht ohne gesetzten Mandanten keine Zeilen und kann die Mandanten nicht einmal auflisten. Die Jobs als Eigentümer laufen zu lassen, würde Row-Level Security genau aus dem Code entfernen, der später Postfach-Tokens verarbeitet. Stattdessen liefert eine abgeschottete Datenbankfunktion nur Mandanten-IDs, und der geplante Job macht daraus eine Queue-Nachricht pro Mandant.

Den schwierigen Teil übernimmt dann die Queue. Wiederholungen und die Dead-Letter-Queue wirken pro Mandant, ein fehlschlagender Mandant hält die anderen also nicht auf. Eine Nachricht, die sich nicht parsen lässt, wird weder verarbeitet noch gelöscht und landet in der Dead-Letter-Queue. Handler berechnen den Sollzustand und wenden nur die Differenz an, eine doppelte Zustellung ändert also nichts. Der erste Job auf dieser Strecke, die Erinnerungen zum Nachfassen, wurde gewählt, um Zeitplan, Verteilung, Queue und Dead-Letter-Queue zu beweisen, bevor Postfach- oder Modell-Code davon abhing. Der Postfach-Abgleich alle 30 Minuten läuft inzwischen denselben Weg.

## Eine Pipeline, die sich nicht durch Überspringen bestehen lässt

Die CI läuft gegen echte Container mit Postgres 17, ElasticMQ und einem IMAP-Server, nicht gegen Mocks, mit reinen Leserechten und jeder GitHub Action auf einen Commit-SHA gepinnt. Die Datenbank- und Queue-Tests werden still übersprungen, wenn diese Dienste fehlen, ein grüner Lauf hätte also nichts bedeuten können. Die Pipeline lässt den Build scheitern, sobald ein Test als übersprungen gemeldet wird. Ein Abhängigkeits-Audit auf Stufe „high“ schließt den Job ab.

## Vom Branch-Push auf den Pi

Ein Deploy ist ein Push auf den Branch `staging`, nie ein Klick und nie ein Force-Push. Die CI baut die drei Images (API, Web, Worker) für arm64, cacht die Layer und legt sie in der GitHub Container Registry ab, getaggt mit `staging` und dem Commit-SHA. Für die Registry meldet sich der Job mit seinem eigenen kurzlebigen Token an, gespeicherte Registry-Zugangsdaten gibt es nirgends. Auf dem Pi holt ein Skript die Images und startet sie mit Docker Compose; der Health-Check der API meldet den ausgelieferten Commit.

Jeder dauerhaft laufende Container läuft mit schreibgeschütztem Root-Dateisystem, ohne Linux-Capabilities, ohne Rechteausweitung und mit rotierten Logs, damit Logs die Platte nicht füllen. Die API startet erst, wenn der Migrations-Job sauber beendet ist, der Web-Container erst, wenn die API gesund ist. Nur der Web-Container veröffentlicht einen Port, gebunden an localhost. Tailscale Serve stellt privates HTTPS davor, nichts ist im lokalen Netz oder im Internet erreichbar.

Die ersten Deploys fanden echte Probleme, jedes in der Pipeline behoben statt von Hand:

## Eine öffentliche Adresse, die nichts preisgibt

<a href="https://whocalledback.com" target="_blank" rel="noopener noreferrer">whocalledback.com<span class="sr-only"> (öffnet in einem neuen Tab)</span></a> ist eine Coming-soon-Seite, ausgeliefert von einem Cloudflare Worker im kostenlosen Tarif, ohne Server dahinter. Die Weiterleitungen auf HTTPS und von `www` stehen im Code des Workers, nicht in einer Dashboard-Einstellung. Die Seite sendet HSTS und eine strenge Content Security Policy, setzt keine Cookies und stellt keine Anfragen an Dritte. Sie wählt Deutsch für die Zeitzonen der DACH-Region und sonst Englisch, ohne IP-Abfrage; dieselbe Regel funktioniert so auch auf dem Pi, der nicht hinter Cloudflare steht. Live geprüft mit curl und einem Headless-Browser: `http://` und `www` antworten mit 301 auf die HTTPS-Domain, der Pfad bleibt erhalten, und die Seite antwortet mit 200 und beiden Headern.

## Personenbezogene Daten bleiben aus Logs und Modell heraus

Logs sind JSON, ihre Felder sind IDs, Zählerstände und Codes: keine E-Mail-Inhalte, Datenbank-Fehlermeldungen oder Abfragetexte. Das Sprachmodell bekommt nur, was eine Aufgabe braucht. Die Klassifizierung sieht Absender, Betreff und die ersten 2.000 Zeichen, gespeichert wird nichts. Entwürfe zum Nachfassen sehen Unternehmen, Position, Daten und Namen der Kontakte, nie Notizen, Links, Adressen oder den eigenen Namen der Person; die Grußformel ergänzt der Browser. Beide Funktionen sind auf eine Allowlist beschränkt, bis der Auftragsverarbeitungsvertrag des Anbieters geprüft ist, durch ein Monatsbudget pro Mandant gedeckelt und loggen nur Fehlerarten. Die Datenschutzerklärung wurde im selben Pull Request angepasst.

## Kosten formen den Entwurf

Phase 1 kostet nichts: das kostenlose Kontingent von Neon, GitHub Actions und seine Container Registry, ein Cloudflare Worker im kostenlosen Tarif, Tailscale und eigene Hardware. Vor dem AWS-Meilenstein entsteht keine kostenpflichtige AWS-Ressource. Die Obergrenze von etwa 20 € im Monat für Phase 2 hat den Entwurf bestimmt: kein VPC und kein NAT-Gateway (die Lambdas bleiben außerhalb eines VPC und erreichen Neon über den öffentlichen Endpunkt), Rechenleistung, die auf null skaliert, und Zeitpläne passend zur kostenlosen Datenbank. Jeder geplante Lauf weckt die kostenlose Rechenleistung von Neon, daher läuft der Postfach-Abgleich alle 30 Minuten und der Erinnerungs-Job einmal am Tag. Die Modellkosten werden pro Person erfasst.
