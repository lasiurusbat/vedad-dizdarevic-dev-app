## Architecture

Two paths run through it: releases and requests. The buttons above the diagram trace each one and dim the rest. There is no database and no server-side session; the app is stateless.

## Build once, ship that image

<TradeOff
  gained="The image that passed the tests is the image that runs. Nothing is rebuilt between CI and production."
  price="Chrome cannot run inside the slim image, so the browser tests run on the runner instead, before anything is pushed."
/>

- **Two stages.** The first stage builds wheels; the runtime stage installs from them with `--no-index`, so the image has no compiler and no system packages.
- **Non-root.** The app runs as a system user with no login shell and needs no writable path.
- **Self-describing.** Version and commit are build arguments, written into the OCI labels, the environment and every page footer. The image, the registry and the running site all name the same build.
- **A health check that ignores upstreams.** It fetches the home page, which calls no external service, so a weather API outage never marks a healthy container unhealthy.
- **Tuned for the workload.** gunicorn runs one worker with four threads: the app waits on two APIs, and one process keeps its geocoding cache warm.
- **Same image locally.** Docker Compose builds the app and a test service from one anchor, with `pull_policy: build`, so a test run never uses a stale local image.

## A release is a git tag

<TradeOff
  gained="Releasing is one command, and only reviewed code on main can become a release."
  price="A rerun replays the commit the tag points at, so a later fix never reaches it. A published tag is never moved; a mistake means a new version."
/>

One GitHub Actions workflow behaves in two ways. A pull request or a push to `main` builds the image, runs the offline tests inside it and the browser tests on the runner, and stops. A tag runs the same checks, then checks the tag format and that the tag is on `main`, pushes the tested image to Docker Hub under that tag, and hands over to the deploy job.

- **A gate that cannot pass empty.** A skipped suite would still report success, so a missing browser fails the run instead.
- **One image tag per release.** Semantic tags, never `latest`, never a re-pushed tag.
- **Releases are never cancelled halfway.** Newer pushes cancel stale runs, except on tags.
- **Updates go through the same gate.** Dependabot opens weekly grouped pull requests for Actions, pip and the base image, and each merges only when the pipeline is green.

## Check the outcome, not the action

<TradeOff
  gained="A deploy counts only when the live domain answers with the new version, not when a hook returns 200."
  price="A slow DNS change or a slow image swap fails the release run even when the deploy itself worked. The runbook says how to read that failure."
/>

The Render service is image-backed: Render pulls from Docker Hub and never runs the Dockerfile. Two settings that look minor carry the design:

- **Auto-deploy is off.** Left on, any pushed image would redeploy the stored fallback tag, which is how an old version silently comes back.
- **A deploy is a hook call with the exact image tag.** Saving a new image URL in Render's settings deploys nothing, and the old container keeps serving with no sign of it.

After the hook, the smoke test requests the live domain for up to three minutes (12 tries, 15 seconds apart) until the page says `Version X.Y.Z`.

## Fail closed

<TradeOff
  gained="Pull requests, including those from forks and Dependabot, can never push an image or deploy."
  price="Every secret is set by hand, in GitHub and in Render's dashboard. Missing and under-scoped secrets broke the first release twice."
/>

- **Secrets only on tag runs.** The workflow token is read-only, and the deploy job runs in a `production` environment, where required reviewers are one setting away.
- **Security headers on every response.** `default-src 'none'`, everything else `'self'`, no `unsafe-inline`, plus `X-Frame-Options`, `nosniff`, a referrer and a permissions policy. HSTS is sent only over HTTPS and without `includeSubDomains`, so a mistake cannot lock the domain's other uses. Tests hold all of it.
- **No third-party requests.** Fonts are self-hosted.
- **The API key never reaches a log.** It travels in a query string, so the code logs only status codes and exception classes; a test holds this.
- **A small attack surface.** A non-root container with no system packages and no database.

## Free tiers that fail well

<TradeOff
  gained="Hosting and CI cost nothing, on every service."
  price="Rate limits the app cannot raise: on October 29 every live forecast failed, because the free forecast API limits by IP and Render's egress IP is shared."
/>

The response to that incident came in layers:

1. **Make it visible.** The failure reason is now logged, so the next occurrence is diagnosed from logs, not guessed.
2. **Call less.** A server-side cache keeps a good forecast for ten minutes; failures are never cached. Crawlers get a crawl delay.
3. **Add a second source.** When Open-Meteo refuses, OpenWeather answers, translated into Open-Meteo's shape so nothing above the client knows which one replied. It runs within a self-imposed daily budget of 900 calls, because that provider bills past its free tier, and it leaves unknown values unknown.
4. **Degrade honestly.** A broken upstream returns `503` and a missing city `404`, never a `200` that says "not found".

An uptime check pings the home page. It calls no upstream API, so it proves DNS, the certificate and the version, and it keeps the free instance from sleeping.

## Problems I hit

The first release took five attempts, and every failure was a missing piece of the pipeline, not an application bug. Every release since has been green on the first attempt.

## The workload

<ThemedScreenshot
  light={appPanel}
  placement="natural"
  alt="The Rain Alert forecast panel for Dublin: the city name, a rain warning, the hour-by-hour chart with a marker at 18:00, today’s summary and the seven days with their rain chances."
  caption="The forecast panel, rendered on the server for every day, so it works without JavaScript."

The platform runs a small, stateless Flask app. Type a city and it shows the chance of rain for seven days, with an hourly strip, a three-band scale, browser alerts and a calendar export of the wet days. Preferences stay in the browser, so there are no accounts and no personal data on the server. It is an installable web app whose service worker caches the shell and never the forecast. Weather data comes from Open-Meteo under a non-commercial licence, so the app stays free, with donations as the only income.
