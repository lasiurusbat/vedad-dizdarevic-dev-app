## Scope

Sorted is a commercial SaaS product, live at [sorted.onl](https://sorted.onl): self sign-up, Stripe billing and custom plans for support teams. I own the platform end to end: the infrastructure, the pipelines and the operations, plus the application they run. I built it in six weeks (September 17 to October 31, 2026). This write-up describes the production configuration, defined in Terraform and reviewed. The cost figures are my own estimates from the docs in the repository, not billing data, and failover has been designed but not drilled.

## Architecture

The request path is browser, Cloudflare, an ALB with an ACM certificate, nginx and the Bun server in one Fargate task, then RDS PostgreSQL in private subnets. The mail path is customer email, SES receipt rule, S3 (own KMS key) and SNS, a signed webhook on the ALB, a saved ticket, a `pg-boss` job for AI classification, then either the agent queue or an automatic reply out through SES, with delivery events coming back through SNS.

## Infrastructure highlights

- **Compute.** One Fargate task with two containers, on ARM64 for about 20 % lower cost. Rolling deploys use the deployment circuit breaker with automatic rollback, and every database migration must work with the previous release (expand, then contract).
- **Network.** Security groups reference each other, not CIDRs. RDS accepts connections only from the task. There is no SSH and no bastion; ECS Exec is the break-glass path.
- **Data.** Private RDS with encryption, a staged rollout of database TLS (`off`, `verify`, `require`) and secrets injected from Secrets Manager.
- **Mail and attachments.** SES, SNS and S3 form the inbound pipeline. Webhooks trust only SNS signatures, the inbound bucket has its own KMS key, and GuardDuty Malware Protection scans every attachment.
- **Delivery.** A release is a git tag that runs the full check suite and pushes immutable images. Deploying is a reviewed infrastructure change; the workflow writes the plan into the run summary and applies that exact saved plan. Infrastructure CI runs `terraform fmt`, `validate`, and 22 offline `terraform test` runs with mocked providers that assert the security properties without an AWS account.
- **Operations.** Structured JSON logs, Grafana Cloud reading CloudWatch through a read-only role with an External ID, alerts tied to a symptom-first runbook.

## How a release gets there

Two repositories, two roles, no stored keys. The application repository turns a git tag into an immutable image; the infrastructure repository decides which image runs, through a reviewed Terraform change.

## Monitoring: CloudWatch and Grafana

CloudWatch holds the data; Grafana Cloud reads it in place, so nothing is shipped or copied. Terraform creates a read-only IAM role that Grafana's AWS account can assume only with the stack's External ID (protection against the confused deputy), limited to CloudWatch metrics and that environment's log group.

- **Logs.** Containers log to `/ecs/sorted-<env>` in CloudWatch Logs, 30 days in prod and 7 in dev. The server writes structured JSON with a request ID, so one Logs Insights query follows a user's `X-Request-Id` through the system.
- **Metrics.** The AWS namespaces for the ALB, ECS, RDS and SES, plus Container Insights in prod for the running task count.
- **Uptime.** Synthetic checks probe the site and `/api/health`, which also checks the database.
- **Spot visibility.** An EventBridge rule writes every `SpotInterruption` task stop into its own log group, so any restart is explainable.
- **Alerts and runbook.** Rules on the same signals as the dashboard, each mapped to a section of a symptom-first runbook: the first five minutes, rollback, and the failure modes I actually hit.

## The workload

The platform exists to run this application.

Each customer team gets a Sorted address or forwards its own in. An incoming email becomes a ticket. AI classifies it, summarizes it and, for non-transactional questions, answers from the team's knowledge base. **Refund and payment tickets never go to the AI.** Humans work a queue: assign, reply, merge, templates, audit log. It is multi-tenant SaaS with self sign-up, Stripe billing, three team roles, 22 UI languages and a super-admin console. All screenshots below use demo data.

Three structural rules keep the AI safe:

1. **The webhook never calls the AI.** It saves the message and returns 200, so AI latency or failure cannot lose a customer's email.
2. **Guardrails are code, not prompt text.** The model returns category, priority, confidence and a draft. Application code decides whether anything is sent.
3. **Every AI failure ends with the ticket open for a human.** A sweep every five minutes opens anything a crash left behind.


## Limitations and what I would do next

- **One task.** The database fails over across zones, but the single app task is restarted by ECS in the other zone, a short interruption. I have not tested it under load or a real failover, and there is no autoscaling yet.
- **The deploy role is an administrator.** This is a deliberate trade-off with tight trust conditions. A permission boundary and a scoped policy generated from a plan would be a better end state.
- **Alert rules live in Grafana, not in Terraform.** Only the IAM role is code today.
- **Terraform state holds generated secrets in plain text.** The bucket is private and encrypted, but I would create those secrets outside state or rotate them on a schedule.
- **Backup restore is documented but not drilled.** Both the RDS snapshot and the Deep Archive path need a scheduled restore test.
- **No WAF rules of my own.** I would add rate-based rules and test them against the SES and Stripe webhooks first, because a challenge on those paths would silently break mail and billing.

I do not claim a formal security audit. I used review passes while building.
