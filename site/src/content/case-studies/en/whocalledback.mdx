This page is a work in progress, written on purpose before the project is finished. It says what is designed, what is built, what has been checked and what has not. Each section is labelled the same way, so a plan is never mistaken for a result.

## Two phases, one codebase

The aim is to build for a cloud target without paying for the cloud during development. Phase 1 runs on a Raspberry Pi 5 with Docker Compose, a free Neon Postgres database in Frankfurt and private access over Tailscale. Phase 2 moves the same code to Lambda, SQS, EventBridge Scheduler, S3 and CloudFront, defined with Terraform and deployed through GitHub OIDC. The Pi and Lambda are both arm64, so one build target serves both.

## Four ports, everything else shared

Only four things genuinely differ between the Pi and AWS. Each is a small interface with one implementation per environment. Business logic depends on the interfaces only, so environment-specific code lives in entrypoints and adapters and nowhere else.

| Concern | Raspberry Pi | AWS |
| --- | --- | --- |
| Queue | ElasticMQ | SQS |
| Schedules | cron in a container | EventBridge Scheduler |
| Token encryption | local AES-GCM key file | KMS |
| Outgoing email | none | SES |

The queue handlers are plain functions that take a batch and return the failed message IDs, which is the Lambda partial-batch-response shape. On the Pi a poller calls them; on AWS the Lambda runtime does. The Pi adapter is the AWS SDK pointed at ElasticMQ, so the Pi already exercises the real client code.

<TradeOff
  gained="One set of handlers, tested the same way in both environments, and an environment switch that touches four adapters."
  price="ElasticMQ is not SQS and a Pi is not Lambda. The real differences will only show during the AWS migration, and the plan budgets time to write them down."
/>

## Isolation enforced by the database

Other people’s recruiter names and email metadata will live in this system, so a missing filter in application code must not leak a tenant’s rows. Row-level security in Postgres enforces the boundary: one policy per tenant table, forced on, failing closed when no tenant is set. Two application roles cannot bypass it. The roles are created in SQL migrations, never in a cloud console, because a role created there silently inherits a bypass and every policy stops applying. Every server process also refuses to start if its database role is a superuser, bypasses row-level security or owns tables.

<TradeOff
  gained="Isolation that holds when application code has a bug, with tests that fail if a tenant table lacks a policy or a grant."
  price="Row-level security does not contain SQL injection, and the migration tooling cannot express the forced policies, so each tenant table needs a hand-written follow-up migration."
/>

## A pipeline that cannot pass by skipping

CI runs against real Postgres and ElasticMQ containers, not mocks. The database and queue tests skip silently when those services are missing, so a green run could have meant nothing. The pipeline now fails the build if any test reports skipped. The Pi runtime hardens every long-running container: read-only root filesystem, all capabilities dropped, rotated logs. A one-shot migration container is the only part that ever sees the owner database credential.
