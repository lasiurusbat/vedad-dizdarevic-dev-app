This page is a work in progress, written on purpose before the project is finished. It says what is designed, what is built, what has been checked and what has not, so a plan is never mistaken for a result. Phase 1 runs on a Raspberry Pi as the `staging` environment since November 11, 2026, and syncs the owner’s own mailbox every 30 minutes. Since November 13, <a href="https://whocalledback.com" target="_blank" rel="noopener noreferrer">whocalledback.com<span class="sr-only"> (opens in a new tab)</span></a> shows a public coming-soon page; the app itself stays private.

## Two phases, one codebase

The aim is to build for a cloud target without paying for the cloud during development. Phase 1 runs on a Raspberry Pi 5 with Docker Compose, a free Neon Postgres database in Frankfurt and private access over Tailscale. Phase 2 moves the same code to Lambda, SQS, EventBridge Scheduler, S3 and CloudFront, defined with Terraform and deployed through GitHub OIDC. The Pi and Lambda are both arm64, so one build target serves both.

## Four ports, everything else shared

Only four things genuinely differ between the Pi and AWS. Each is a small interface with one implementation per environment. Business logic depends on the interfaces only, so environment-specific code lives in entrypoints and adapters and nowhere else. Postgres is the same in both phases, so it gets no port.

| Concern | Raspberry Pi | AWS |
| --- | --- | --- |
| Queue | ElasticMQ | SQS |
| Schedules | cron in a container | EventBridge Scheduler |
| Token encryption | local AES-GCM key file | KMS |
| Outgoing email | none | SES |

The queue handlers are plain functions that take a batch and return the failed message IDs, which is the Lambda partial-batch-response shape. On the Pi a poller calls them; on AWS the Lambda runtime does. The Pi adapter is the AWS SDK pointed at ElasticMQ, so the Pi already exercises the real client code. Security rules belong to the port, not the adapter: the token cipher must bind every encryption to the tenant and the connection, as associated data on the Pi and as KMS encryption context on AWS.

<TradeOff
  gained="One set of handlers, tested the same way in both environments, and an environment switch that touches four adapters."
  price="ElasticMQ is not SQS and a Pi is not Lambda. The real differences will only show during the AWS migration, and the plan budgets time to write them down."
/>

## Isolation enforced by the database

Other people’s recruiter names and email metadata live in this system, so a missing filter in application code must not leak a tenant’s rows. Row-level security in Postgres enforces the boundary: one policy per tenant table, forced on, failing closed when no tenant is set. The tenant is set only inside a transaction, so the setting cannot leak through a pooled connection. Foreign keys include the tenant ID, because Postgres does not apply row-level security to foreign-key checks.

Two application roles cannot bypass the policies. They are created in SQL migrations, never in the Neon console, because a role created there joins a group that bypasses row-level security, and every policy would silently stop applying. Every server process also refuses to start if its database role is a superuser, bypasses row-level security, belongs to another role or owns tables. Only the one-shot migration job ever sees the owner credential.

<TradeOff
  gained="Isolation that holds when application code has a bug, with tests that fail if a tenant table lacks a policy or a grant."
  price="Row-level security does not contain SQL injection, so queries stay parameterized. The migration tooling cannot express the forced policies, so each tenant table needs a hand-written follow-up migration."
/>

## Scheduled work fans out through the queue

Background jobs must act on every tenant, but the tenant role cannot see any rows without a tenant set, so it cannot even list the tenants. Running the jobs as the owner would remove row-level security from exactly the code that will later handle mailbox tokens. Instead, one locked-down database function returns tenant IDs and nothing else, and the scheduled job turns them into one queue message per tenant.

The queue then does the hard parts. Retries and the dead-letter queue work per tenant, so one failing tenant does not block the rest. A message that does not parse is neither processed nor deleted, and ends up in the dead-letter queue. Handlers compute the desired state and apply the difference, so a duplicate delivery changes nothing. The first job on this pipeline, follow-up reminders, was chosen to prove schedule, fan-out, queue and dead-letter queue before any mailbox or model code depended on them. The 30-minute mailbox sync now runs on the same path.

## A pipeline that cannot pass by skipping

CI runs against real Postgres 17, ElasticMQ and IMAP containers, not mocks, with read-only permissions and every GitHub Action pinned to a commit SHA. The database and queue tests skip silently when those services are missing, so a green run could have meant nothing. The pipeline fails the build if any test reports skipped. A dependency audit at high severity closes the job.

## From a branch push to the Pi

A deploy is a push to the `staging` branch, never a click and never a force push. CI builds the three images (API, web, workers) for arm64, caches the layers and pushes them to the GitHub container registry, tagged `staging` and with the commit SHA. The job’s own short-lived token signs in to the registry, so no registry credential is stored anywhere. On the Pi, one script pulls the images and starts them with Docker Compose; the API’s health check reports the deployed commit.

Every long-running container runs with a read-only root filesystem, all Linux capabilities dropped, no privilege escalation and rotated logs, so logs cannot fill the disk. The API starts only after the migration job exits cleanly, and the web container only after the API is healthy. Only the web container publishes a port, bound to localhost. Tailscale Serve puts private HTTPS in front of it, so nothing is open to the local network or the internet.

The first deploys found real problems, each fixed in the pipeline rather than by hand:

## A public front door that exposes nothing

<a href="https://whocalledback.com" target="_blank" rel="noopener noreferrer">whocalledback.com<span class="sr-only"> (opens in a new tab)</span></a> is a coming-soon page served by a Cloudflare Worker on the free plan, with no server behind it. The HTTPS and `www` redirects live in the Worker’s code, not in a dashboard setting. The page sends HSTS and a strict content security policy, sets no cookies and makes no third-party requests. It picks German for the DACH time zones and English elsewhere, with no IP lookup, so the same rule works on the Pi, which is not behind Cloudflare. It was checked live with curl and a headless browser: `http://` and `www` answer 301 to the HTTPS apex with the path kept, and the page answers 200 with both headers.

## Personal data stays out of logs and the model

Logs are JSON, and their fields are IDs, counts and codes: no email bodies, database error messages or query strings. The language model gets only what a task needs. Classification sees the sender, the subject and the first 2,000 characters, and nothing is stored. Follow-up drafts see the company, position, dates and contact names, never notes, links, addresses or the user’s own name; the closing is added in the browser. Both features are limited to an allowlist until the provider’s data processing agreement is verified, capped by a monthly budget per tenant, and log only error types. The privacy policy was updated in the same pull request.

## Cost shapes the design

Phase 1 costs nothing: the Neon free tier, GitHub Actions and its container registry, a Cloudflare Worker on the free plan, Tailscale and owned hardware. No paid AWS resource comes before the AWS milestone. The Phase 2 ceiling of about €20 a month drove the design: no VPC or NAT gateway (the Lambdas stay outside a VPC and reach Neon over its public endpoint), compute that scales to zero, and schedules sized to the free database. Every scheduled run wakes Neon’s free compute, so the mailbox sync runs every 30 minutes and the reminder job once a day. Model cost is tracked per user.
